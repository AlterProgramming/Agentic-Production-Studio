# Fresh-Session Prompt

Use this prompt to start one uncontaminated Progressive Design benchmark session.

---

You are running one isolated Progressive Design benchmark from a blank implementation state.

## Inputs

You will receive:

1. A frozen product brief and immutable content fixtures.
2. The canonical Progressive Design doctrine.
3. One assigned experimental condition: A, B, C, or D.
4. A route, state, and evidence contract.
5. An experiment manifest location.

You will not receive an existing site, starter design, component library, visual reference implementation, or prior condition source.

Do not inspect prior experiments, comparison images, winning implementations, or source from another condition.

## Objective

Create the strongest complete product experience supported by the frozen material under your assigned condition.

The frozen brief—not a prior interface—is the foundation. Preserve all required facts, copy, data, functionality, routes, states, constraints, and approved assets. Do not invent sections, filler, fake data, decorative complexity, or explanatory design rationale.

You are responsible for originating the information architecture, composition, interaction model, responsive behavior, and visual expression from the blank state.

## Blank-State Contract

Begin with an empty assigned source directory.

Do not:

- reconstruct or imitate a previously tested site;
- assume an existing hierarchy, grid, page composition, component system, or visual identity;
- treat another condition as a draft to improve;
- inherit CSS, components, scripts, generated assets, layout templates, or design tokens;
- preserve arbitrary visual decisions that are not present in the frozen brief.

What must remain constant across conditions is the product problem and evidence contract—not the design solution.

## Isolation

Create all implementation code inside your assigned condition directory.

Do not import CSS, components, scripts, generated assets, design tokens, or templates from another condition. Shared input is limited to immutable fixtures explicitly named by the manifest.

Record in the isolation receipt:

- whether the source directory was empty at initialization;
- whether any implementation code was shared;
- whether any prior output was seen;
- the implementation budget used;
- any unavoidable environmental differences.

## Condition Behavior

### Condition A — Control

Use ordinary strong product-design judgment. Starting from the blank state, produce a polished, responsive, credible implementation. Do not use the Progressive Design doctrine.

### Condition B — Progressive

Starting from the blank state, apply the Progressive Design layer across:

- integrity;
- composition;
- system;
- identity;
- interaction;
- authorship;
- critique and elevation.

Integrity means faithful translation of the frozen brief, not preservation of an existing interface. Establish the necessary lower levels, but do not distribute effort evenly or stop once the result is merely clean and functional. Progress toward the highest level the material can support.

### Condition C — Spatial

Apply Condition B plus Spatial Intelligence. You may use a private construction layer while originating the design. Public geometry must improve orientation, comparison, sequence, causality, scale, or spatial understanding. Do not expose geometry merely to signal sophistication or reveal how the page was constructed.

### Condition D — Reconciled

Apply Conditions B and C internally, then perform Visitor-Facing Reconciliation. Preserve useful structural intelligence while removing or translating construction aids, diagnostic language, implementation vocabulary, design rationale, unexplained numbering, generalized diagrams, technical status treatments, and motion that advertises itself. The visitor must encounter meaning before mechanism.

Condition D is not a revision of Condition C. It is an independent blank-state implementation governed by the combined doctrine.

## Required Process

1. Read and hash the frozen brief.
2. Confirm that the assigned source directory begins empty.
3. Confirm the assigned source and evidence boundaries.
4. Extract the facts, actions, routes, states, constraints, and approved assets that must remain constant.
5. Originate and implement the complete experience under the assigned condition.
6. Render the required desktop and mobile evidence.
7. Validate routes, links, application state, overflow, keyboard focus, contrast, legibility, and reduced motion.
8. State the actual validation boundary. Do not imply browser-engine coverage when only static or script-level checks ran.
9. Produce the condition evidence index and isolation receipt.
10. Do not evaluate or compare your condition against another condition.

## Required Evidence

Produce:

- desktop primary-page render;
- desktop secondary-page render;
- mobile primary-page render;
- mobile interaction-state render;
- route and link validation;
- application-state validation;
- responsive overflow check;
- keyboard and focus check;
- contrast and legibility review;
- reduced-motion review;
- frozen-content fidelity note;
- blank-state and isolation receipt.

## Public-Surface Restrictions

Do not expose internal reasoning, agent instructions, verification notes, hierarchy labels, design-system terminology, alignment guides, breakpoint indicators, debug controls, publishing notes, or implementation status in the production interface.

A debug layer may exist for authoring only when the assigned condition permits it. It must default off and must not be required for the public composition to feel complete.

## Completion

The condition is complete only when the implementation, evidence, validations, limitations, frozen-content fidelity note, and blank-state isolation receipt are all present.

Do not declare the experiment winner. Blind comparison happens in a separate evaluation session.
